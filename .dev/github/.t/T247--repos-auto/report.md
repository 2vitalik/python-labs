# T247 · Репозиторії: pull → push щогодини на ноутбуці, сервер — пізніше — звіт

`2026-10-29` · ⚙️ задача · план — `plan.md` · механіка доступу — [T48](../T48-C--collaborator-access.md) · дизайн — [T235](../T235-P--lab-deadlines-design.md)

## Сервер чи ноутбук

Питання: клонувати репозиторії студентів на сервері (треба дати серверу доступ до всіх моїх репозиторіїв?) чи локально, а на сервер слати лише факти через API.

- **Що потрібно серверу.** Репозиторії приватні, доступ — через те, що студент додав `2vitalik` колаборатором. Сервер мусить автентифікуватись чимось від акаунта `2vitalik` (або іншого акаунта, якого студенти теж додадуть).
- **Чим можна.** Перевірено 2026-10-29 за доками GitHub ([Managing your personal access tokens](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens), список обмежень fine-grained токенів): **fine-grained PAT не бачить чужих репозиторіїв, де ти лише колаборатор** — токен привʼязаний до одного власника ресурсів (ти або організація) і його репозиторіїв. Тобто «токен лише на читання студентських репозиторіїв» для акаунта `2vitalik` зробити не можна. Лишаються:
  - classic PAT зі scope `repo` або SSH-ключ акаунта `2vitalik` на сервері — обидва дають **читання і запис до всіх репозиторіїв 2vitalik** (колаборатор у GitHub — це право push). Компрометація сервера = компрометація всього GitHub. Не робимо.
  - machine user (окремий акаунт-бот курсу) або GitHub App — токен на сервері відкриває лише студентські репозиторії, але **кожен студент має зробити дію** (додати другого колаборатора чи встановити застосунок). 72 студенти вже додали `2vitalik`; просити ще раз посеред семестру — ціна, що не окупається.
- **Ноутбук.** SSH-ключ `2vitalik` лежить у `~/.ssh` під v6u, за межі машини не виходить; на сайт іде лише те, що він і так показує (посилання, гілка, журнал комітів). Усе вже є з T237 — бракувало лише запуску за розкладом.
- **Ціна ноутбука.** `seen` (коли коміт уперше побачили) залежить від того, чи не спить ноутбук: пропущені години launchd зводить в один запуск після пробудження; верхня межа лишається чесною, лише грубшою. Звіти агента й так пишуться тут — субагенти читають клони на цій машині (на сервері LLM лише за API, T182).
- **Висновок:** зараз — ноутбук, щогодини. Сервер — коли зʼявиться потреба в кнопці «Оновити» чи вебхуках: тоді machine user або GitHub App ([T48](../T48-C--collaborator-access.md) c/d), з окремим проханням до студентів.

## Зроблено

- **`bin/repos auto`** — `sync` → `pull` → `push` одним викликом, рядок із часом на початку (для журналу). `pull` повертає, чи GitHub узагалі відповів: якщо жодного репозиторію не дістали — `push` не йде («GitHub недосяжний — на сайт нічого не шлю»).
- **Тимчасові помилки** — `core/repos.py`: `OFFLINE` («нема звʼязку з GitHub»: `Could not resolve host`, `Network is unreachable`, `Connection timed out`) і `TIMEOUT` зібрані в `TRANSIENT`; `pull` їх друкує, але **не записує** в `.state.json` — попереднє слово про доступ лишається, ⚠️ на сайті від вимкненого Wi-Fi не зʼявиться.
- **Порожній репозиторій** (створено, жодного коміту): `git remote set-head origin -a` каже «Cannot determine remote HEAD» → «репозиторій порожній: жодного коміту», а не сирий `--detach does not take a path argument`. `set-head` + `checkout --detach` тепер і після `clone`, не лише після `fetch` — свіжий клон порожнього репозиторію дає те саме слово одразу.
- **`bin/repos launchd on|off`** — пише `~/Library/LaunchAgents/com.vitalik.python-labs-repos.plist` зі справжніх шляхів (інтерпретатор venv, скрипт, корінь проєкту) і робить `launchctl bootstrap gui/<uid>`; `StartInterval` 3600 + `RunAtLoad`; журнал — `~/Library/Logs/python-labs-repos.log`; `off` — `bootout` і прибирає файл. Чому щогодини, а не 23:30 (T236 Q4): дедлайн о 23:59, добовий запуск о 23:30 не бачив би останні пів години; щогодинний `fetch` 72 репозиторіїв — ~40 с.

## Перевірено

- `./bin/repos auto` на проді 2026-10-29: `sync` — 109 студентів, 72 з посиланням; `pull` — клоновано 22, оновлено 45, помилок 5 (3 «не знайдено або нема доступу», 1 порожній, 1 — зникла після виправлення); `push` — надіслано 72; 43 с. `GET /api/labs` на проді: 67 репозиторіїв ok, 5 з помилкою, 37 без посилання.
- Порожній репозиторій: `pull` наявного клону і свіжий клон у тимчасову теку — обидва «репозиторій порожній: жодного коміту»; здоровий поруч — без змін.
- `reason()`: `Network is unreachable` і `Could not resolve host` → `OFFLINE` ∈ `TRANSIENT`.
- plist, який пише `launchd on`, зібрано в тимчасову теку — `plutil -lint` ok.
- `ruff` — лише три давні зауваження в цих файлах (noqa, `timezone.utc`, `check=`), нових нема.

## Не перевірено

- Сам агент launchd: `launchctl bootstrap` — встановлення фонового агента — Claude Code у цьому режимі не дозволяє; **Vitalik запускає `bin/repos launchd on` сам** (раз, під v6u, у корені проєкту) і дивиться `~/Library/Logs/python-labs-repos.log` після першого запуску (`RunAtLoad`). Якщо SSH у launchd не підхопить ключ (у термінальній сесії агент ssh без identities, а `ssh -T git@github.com` працює — ключ без пароля), у журналі буде «GitHub не прийняв SSH-ключ» для всіх і «на сайт нічого не шлю» не спрацює (це не `TRANSIENT`) — тоді сказати мені.
- Офлайн-гілка `auto` наживо (лише `reason()`).

## Спостереження

- `data/repos/` лежить у Dropbox: щогодинний `fetch` ворушить `.git` 72 клонів (8.6 МБ) — Dropbox їх синхронізує другому користувачу. Поки терпимо; якщо заважатиме — винести теку за межі Dropbox змінною.
