## Навіщо системі код студента (зведення споживачів)

- ШІ-передперевірка заявок: «завдання X справді реалізоване?» ([T09](../../reports/.t/T09-C--reports-concept.md)).
- Підказки цілей для зауважень: файли/класи/функції ([T13](../../remarks/.t/T13-C--remarks-concept.md)).
- Аналіз історії комітів: дедлайни (що було зроблено до дати), динаміка роботи.
- У добу ШІ-кодогенерації git-історія — чи не головний доказ **процесу** роботи: рівний потік осмислених комітів проти «одного коміту на 3000 рядків за ніч перед дедлайном». Це аргумент на захисті, а не автоматичний вирок.

## Варіанти доступу (порівняння)

- a) **GitHub App/бот курсу** — студент додає бота колаборатором у свій приватний репозиторій (або репозиторій створюється в органзації курсу). Плюси: стандартно, безпечно, webhook-и «з коробки» (пуш → система оновила стан), API історії. Мінуси: студентам потрібен GitHub (для програмістів — не мінус). **Рекомендую**; варіант з організацією курсу (репозиторії створює система з шаблону-скелета) — найкерованіший: єдина структура, твій доступ гарантований назавжди.
- b) OAuth від твого акаунта + студенти дають тобі доступ — просто, але вручну і без webhook-ів.
- c) Завантаження архівів коду на сайт — без історії, зайва ручна робота; хіба що fallback.
- d) Власний git-сервер (Gitea) на VPS — повний контроль, але зайва інфраструктура; GitHub цінніший студентам як портфоліо.

## Механіка (при варіанті a)

- Push → webhook → система клонує/оновлює копію на VPS → індексує структуру (файли/класи/функції) → фонові перевірки: ШІ-звірка заявлених завдань, чернетки зауважень, дедлайн-зрізи.
- Дедлайн-зріз = стан репозиторію на коміт до моменту дедлайну — автоматично, чесно, без суперечок.
- Обмеження: приватні репозиторії (код студентів не публічний), токени зберігаються на VPS, доступ — тільки читання.
