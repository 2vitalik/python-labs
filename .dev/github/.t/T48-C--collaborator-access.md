# T48 · Доступ через колаборатора: механіка й авторизація

`2026-07-26` · 🔆 clarification

Контекст:
- питання Vitalik у чаті 2026-07-26: якщо студенти додають мене колаборатором у свої репозиторії — чи зможе сервер автоматично їх клонувати й аналізувати, і що для цього треба;
- це механіка варіанта «особисті репозиторії + колаборатор» з [T15](T15-C--github-integration.md); рішення по моделі доступу лишається за [T16](T16-Q--github-open-questions.md) Q1.

## Коротка відповідь

- Так, технічно працює, але не «автоматично само по собі»: приватний репозиторій git анонімно не віддасть — сервер має автентифікуватися токеном/ключем акаунта-колаборатора.
- Два обовʼязкові кроки: (1) запрошення колаборатора має бути **прийняте**, (2) на сервері лежить токен або SSH-ключ цього акаунта.

## Механіка (як воно працює під капотом)

- «Додати колаборатора» = надіслати запрошення; доступ зʼявляється лише після прийняття; неприйняте запрошення протухає за 7 днів.
- Прийняття автоматизується через API: `GET /user/repository_invitations` → `PATCH /user/repository_invitations/{id}` — скрипт на сервері може приймати все сам.
- Список усіх репозиторіїв, куди додали: `GET /user/repos?affiliation=collaborator` — система сама дізнається про нові репо, нічого руками вводити не треба.
- Клонування: `git clone https://x-access-token:<TOKEN>@github.com/<student>/<repo>.git` (або SSH-ключем акаунта). Git-хуки при clone не виконуються — саме клонування й читання коду безпечні.

## Чим авторизуватись — варіанти

- a) **Особистий акаунт + classic PAT** (`repo` scope) — найпростіше, працює одразу. Мінус критичний: такий токен дає читання **і запис** до всіх твоїх репозиторіїв; компрометація сервера = компрометація всього твого GitHub.
- b) **Особистий акаунт + fine-grained PAT** — з березня 2025 (GA) підтримує й чужі репозиторії, де ти колаборатор; можна дати лише `contents: read`. Краще за (a), але це все одно токен твого акаунта на сервері.
- c) **Machine user (бот курсу) + PAT/SSH** — для студентів UX той самий (додати колаборатором `бота` замість тебе), а токен бота на сервері не відкриває нічого твого. GitHub ToS дозволяє один machine account на людину. Мінімально розумний рівень безпеки.
- d) **GitHub App** — студент один раз ставить застосунок за посиланням і вибирає репозиторій; система отримує короткоживучі installation-токени (1 год, лише `contents: read`), webhook push «з коробки» (пуш → система одразу знає), без танцю із запрошеннями-прийняттями. Найбільш «платформний» варіант, трохи більше початкового налаштування (JWT → installation token; у Python це готові бібліотеки).
- e) **Deploy keys** — окремий SSH-ключ у кожен репозиторій руками студента; незручно й не масштабується, відкидаємо.
- f) **Публічні репозиторії** — авторизація взагалі не потрібна; ціна — код відкритий (списування між студентами).

## Небезпеки

- Головний ризик — не «студенти щось зроблять», а **токен на сервері**: blast radius залежить від варіанта (a — весь твій акаунт; c/d — лише студентські репо).
- Клонувати й статично аналізувати код безпечно; **запускати** студентський код (тести тощо) — лише в пісочниці (Docker без мережі), це окреме рішення.
