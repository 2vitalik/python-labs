## Принцип

- MVP = те, без чого семестр не можна ПОЧАТИ, а не те, без чого його не можна ідеально провести. Все інше догвинчується по ходу семестру (перевага власної системи над Coda — можна допилювати щотижня).
- Порядок диктується залежностями: каталог завдань — серце; без нього нема ні звітів, ні монеток.

## Пропозиція черг

- **Черга 0 — рішення (липень):** відповіді на ключові Q (стек, модель монеток, доступ до git), перенос старих матеріалів (каталог завдань, зауваження, таблички) в чернетки.
- **Черга 1 — MVP до старту семестру:** каталог завдань з цінами (адмінка) → кабінет студента: каталог + заявки + прогрес-бар монеток/балів → твій журнал: група × прогрес → автопідрахунок оцінки. Це вже повністю замінює Coda-формули.
- **Черга 2 — перший місяць семестру:** слоти захистів + зауваження (мінімум: створення/список/закриття) → git-інтеграція (репозиторії, дедлайн-зрізи) → бот-нотифікації.
- **Черга 3 — по ходу семестру:** ШІ-передперевірка заявок, чернетки зауважень, генератор варіантів, пайплайн ідей студентів, опитування.
- **Черга 4 — другий семестр:** курсові/ДСТУ-перевірка (якщо курсовий навесні — саме встигаємо), рекалібрація цін за статистикою, експорт відомості.

## Ризики

- Найбільший обсяг ручної роботи — НЕ код, а **контент**: перенос/ревізія каталогу завдань і цін. Починати з нього паралельно з рішеннями (тому [T06](../tasks/.t/T06-Q--tasks-open-questions.md) Q1 — найважливіше питання проєкту).
- Спокуса перфекціонізму в моделі монеток: для черги 1 достатньо зафіксувати робочу версію правил, калібрування — окремим кроком за даними.
- Одночасно з системою в тебе живий семестр: план має витримувати «система готова на 70%, семестр уже йде».
