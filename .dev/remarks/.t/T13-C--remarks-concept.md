## Ядро (з твого брейндампу)

- Багато зауважень повторюються → каталог **стандартних зауважень** з категоріями (іменування, структура, дублювання коду, магічні числа, обробка помилок, архітектура двіжок/вивід…).
- Швидкий ввід під час захисту: пара літер/пошук → підставилось стандартне зауваження; до нього — конкретика: файл/клас/функція/змінна.
- Система підказує цілі з коду студента («ця функція? цей файл?») — для цього їй потрібен доступ до репозиторію ([T15](../../github/.t/T15-C--github-integration.md)).

## Життєвий цикл зауваження

- Створене (на захисті чи при перевірці) → привʼязане до завдання/студента/місця в коді → студент бачить у себе список → виправив і позначив → перевірка (ШІ або ти) → закрите.
- Незакриті зауваження — природні **ворота** ([T07](../../grading/.t/T07-C--coins-system.md)): завдання не зараховується, поки висять критичні; на 90+ не пускають незакриті зауваження по методичці.

## Про що ти, схоже, ще не думав

- **Каталог зауважень = публічна рубрика якості.** Якщо студенти бачать каталог заздалегідь («за що зазвичай повертають») — це навчальний матеріал і чесні правила гри; кількість зауважень на захистах впаде сама.
- **Частотна статистика** зауважень: по студенту (що йому системно вказувати), по потоку (що погано пояснено в курсі — фідбек для тебе), по завданню (де критерії нечіткі).
- **ШІ-чернетка зауважень:** перед захистом я проганяю код по каталогу стандартних зауважень і готую тобі чернетку — ти на захисті лише підтверджуєш/відхиляєш. Твій «швидкий ввід» стає ще швидшим: не писати, а клікати.
- **Тон і адресність:** стандартні формулювання зауважень пишуться один раз добре (що не так → чому це важливо → як виправити) — і кожен студент отримує якісний фідбек без твоїх повторних витрат.
