## 1. З нуля

**Ембединг** — це перетворення тексту на список чисел однакової довжини (вектор), наприклад 384 або 1024 числа. Робить це нейромережа, яку вчили на мільйонах пар «питання — відповідь», «речення — переклад», «заголовок — стаття»: тексти з однієї пари вона мала ставити поруч, випадкові — далеко. Тому після навчання «поруч» означає «про одне й те саме», навіть коли спільних слів нема.

Аналогія — координати міста на мапі. Двох чисел (широта, довгота) досить, щоб сказати, які міста поруч. В ембединга «координат» сотні, і кожна відповідає якійсь невидимій грані змісту.

**Косинусна близькість** показує, наскільки дві стрілки-вектори дивляться в один бік: 1 — однаково, 0 — під прямим кутом, тобто не повʼязані. Рахують її як суму добутків координат (вектори заздалегідь зводять до довжини 1).

Приклад, порахований цієї ночі моделлю Qwen3-Embedding-0.6B. Речення вигадані, не з лекцій. Запит — **«як перевірити, чи однаковий розкид у двох наборах даних»**:

| «Слайд» | Косинус |
|---|---|
| Критерій Фішера порівнює дисперсії двох вибірок | **0.44** ← перше місце |
| Кореляція показує, наскільки дві величини змінюються разом | 0.43 |
| Критерій Стьюдента перевіряє, чи відрізняються середні двох груп | 0.42 |
| Метод головних компонент зменшує кількість ознак… | 0.41 |
| Метод найменших квадратів підбирає пряму… | 0.36 |

Запит і правильний слайд мають лише одне спільне слово — «двох», тож пошук за словами так само охоче показав би Стьюдента. Ембединг вибрав Фішера, бо «розкид» ≈ «дисперсія». Проте перевага мізерна (0.44 проти 0.43): ембединги — не магія, а ще один сигнал. Шкала в кожної моделі своя (multilingual-e5 на тих самих реченнях дає всім 0.73–0.86), тому важить лише порядок, а не саме число.

**За словами чи за змістом.**

| | За словами (+ форми, опечатки, синоніми) | За змістом (ембединги) |
|---|---|---|
| Знаходить | ті самі слова в будь-якій формі | перефразування, переклад, «своїми словами» |
| Не знаходить | «розкид», якщо на слайді «дисперсія» і цієї пари нема в словнику | інколи плутає схожу тему з потрібною відповіддю; слабкий на коротких абревіатурах («PCA») |
| Пояснення | видно, що саме збіглося | «бо близько» — без пояснення |
| Де працює | у браузері, миттєво | треба модель: API, сервер або браузер |

**Векторна база** — сховище, яке швидко (наближено, з індексами на кшталт HNSW) знаходить найближчі вектори серед *мільйонів*. У нас: у текстах лекцій **3 325 абзаців** (пораховано), плюс 316 слайдів і ~2 тис. ключів — разом ≈ 5–6 тис. векторів. 6 тис. × 1024 числа × 4 байти ≈ 25 МБ (у 384 вимірах ≈ 9 МБ, у int8 — ще вчетверо менше). Перебір «в лоб» — це ~6 млн множень: у numpy одиниці мілісекунд, у браузері десятки (?). **База не потрібна.** Вона має сенс від сотень тисяч векторів або коли дані постійно змінюються й треба фільтрувати разом із вектором.

## 2. Карта підходів

Пошук — це конвеєр. Кожен підхід стоїть на одному з кроків.

```
ЗАЗДАЛЕГІДЬ (офлайн)                     НА КОЖЕН ЗАПИТ
документ ─┬─ форми слів (pymorphy3)       запит ─┬─ форми, опечатки, розкладка
          ├─ ключі слайда (doc2query, LLM)       ├─ синоніми курсу (розширення запиту)
          └─ вектори (ембединги)                 └─ (HyDE: LLM вигадує відповідь)
                                                  ↓
                         кандидати: за словами / BM25 ‖ за вектором ‖ розріджені вектори
                                                  ↓
                                      злиття (RRF) → (переранжування) → результати
                                                  ↓
                                      (RAG: LLM читає знайдене й відповідає)
```

| Підхід | Що робить, просто | У нас |
|---|---|---|
| Підрядок | точний збіг літер | ✅ було |
| Повнотекстовий, **BM25** | рахує слова й дає рідкісним більшу вагу («Фішера» важить більше за «метод»), враховує довжину тексту — так виходить порядок результатів | частково: збіги є, ваги BM25 нема |
| Морфологія: **стемінг / лематизація** | стемінг обрізає закінчення («вибірки» → «вибірк»), лематизація зводить слово до словникової форми | ✅ цієї ночі (словник форм) |
| **Нечіткий пошук** | відстань редагування (скільки літер змінити), інша розкладка, латинка | ✅ цієї ночі |
| **Синоніми / розширення запиту** | до запиту додають синоніми: «PCA» → «метод головних компонент» | ✅ цієї ночі (словник курсу) |
| **doc2query** (розширення документа) | LLM дописує до документа питання, якими його шукатимуть | ✅ цієї ночі — це наші «ключі за змістом» |
| **HyDE** | LLM на льоту пише гіпотетичну відповідь на запит, і шукають уже за нею | ❌ потрібна LLM на кожен запит |
| **Щільні ембединги** | розділ 1 | ❓ про це документ |
| **Розріджені вектори** (SPLADE, BGE-M3 sparse) | модель дає вагу кожному слову словника, навіть тим, яких у тексті нема, — ніби BM25 із вивченим словником синонімів | ❌ для української готових майже нема (?) |
| Мультивекторні (ColBERT) | вектор на кожне слово; точно, але важко | ❌ зайве |
| **Гібрид + злиття RRF** | кілька списків (за словами, за змістом) зводять в один: бал = Σ 1/(60 + місце у списку); бали різних методів калібрувати не треба | ✅ по суті: секції за видом (точні / форми / схоже / синоніми / за змістом) |
| **Переранжування** (cross-encoder, rerank) | повільніша й точніша модель читає пару «запит + кандидат» разом і пересортовує перші 20–100 | ❌ розкіш для 316 слайдів |
| **RAG** | знайти фрагменти й дати їх LLM, щоб вона відповіла | пошук — перша половина RAG; ШІ-помічник курсу міг би брати з нього слайди |

**Звідки ви «щось чули».** 2013 — word2vec (Google): вектор для *слова*, знамените «король − чоловік + жінка ≈ королева». 2019 — Sentence-BERT: вектор для *речення*. Грудень 2022 — OpenAI `text-embedding-ada-002`: дешевий API, разом із ChatGPT почалася хвиля «векторних баз» і RAG; «GPT щось таке робив на початку» — найпевніше, саме про це. Сьогодні найкращі ембединги роблять на основі LLM (Qwen3-Embedding, Gemini Embedding).

## 4. Варіанти для нашого сайту

**(а) Лишити як є: форми, опечатки, словник курсу, ключі слайдів** — розмір **0** (журнал запитів — **S**)
- Що дає студентові: база, з якою порівнюємо решту.
- Що поставити: нічого.
- Ціна: $0; памʼять — 0; миттєво в браузері.
- Ризики: непередбачений запит не знайдеться; якість залежить від ключів, які раз написала LLM.

**(б) Ембединги через API** (Voyage `voyage-4-lite` / `voyage-4`, або `gemini-embedding-001`) — розмір **M**
- Що дає студентові: знаходить слайд за будь-яким перефразуванням, зокрема непередбаченим, і за англійським запитом до українського слайда.
- Що поставити:
  - ключ у `.env`;
  - офлайн-скрипт векторів усіх абзаців / слайдів (файлом у media поруч із `keys.json`);
  - ендпоінт `?q=` → вектор запиту → косинус у numpy → топ-10;
  - кеш однакових запитів;
  - новий вид у рушії.
- Ціна: ≈ $0 (200 млн безкоштовних токенів, далі — центи); +25 МБ памʼяті; +0.1–0.4 с на мережу (?), тож запит іде лише після паузи в наборі або Enter.
- Ризики: сервіс упав — вид «за змістом» просто зникає, решта працює; текст запиту (без імені студента) йде третій стороні; ще один ключ і обліковий запис.

**(в) Мала модель на сервері** (ONNX, CPU: EmbeddingGemma-300m або e5-small; Qwen3-0.6B, якщо є ~1 ГБ вільної RAM) — розмір **M**
- Що дає студентові: те саме, що (б); якість трохи нижча (?).
- Що поставити: `onnxruntime` + `tokenizers` у бекенд; файл моделі на 120–600 МБ на сервері; той самий ендпоінт.
- Ціна: $0; +0.2–1.1 ГБ RAM; 5–30 мс на запит (e5, Gemma) або 0.1–0.3 с (Qwen), на VPS у 2–3 рази повільніше (?).
- Ризики: памʼять скромного VPS (скільки вільно — (?)); оновлювати модель доведеться самим; довший старт після деплою.

**(г) Модель у браузері студента** (transformers.js) — розмір **M–L**
- Що дає студентові: те саме, без сервера; після завантаження працює й офлайн.
- Що поставити: `@huggingface/transformers` у Vue (завантажувати лише на вимогу); файл моделі та вектори слайдів.
- Ціна: сервер — $0; на кожен пристрій 135–215 МБ один раз; 10–50 мс на запит після завантаження (?); перше завантаження — від секунд до хвилини.
- Ризики: слабкі телефони й мобільний трафік; без WebGPU (Safari, старі браузери) повільніше (?); проблеми в студентів важко налагоджувати.

## 5. Рекомендація

**Зараз — (а)** плюс маленький журнал запитів: що шукали, скільки знайшов кожен вид, чи був клік; без імені студента. Через 2–4 тижні (або перед сесією) переглянути запити, що нічого не знайшли або лишились без кліку. Перший і найдешевший крок — дописати пропущене в словник і ключі: журнал сам підкаже, чого бракує. Якщо помітна частка (скажімо, понад 5–10 %) ловиться лише за змістом — **(б) з Voyage `voyage-4-lite`**. Він простіший за (в), бо нічого не тримає в памʼяті VPS, і практично безкоштовний.

Перед вибором моделі — тест на 30–50 справжніх запитів, для кожного відомо «правильний слайд»: LLM їх запропонує, викладач перевірить. Порівняти (а) з (а) + ембедингами на 2–3 моделях. Це пів дня роботи, і він знімає більшість «(?)» щодо української. (в) — запасний шлях, якщо третя сторона неприйнятна. (г) не радимо: 135–215 МБ на кожен студентський телефон заради 316 слайдів.

**Що потрібно від викладача, щоб почати:**
1. **Рішення:** чи можна текст пошукового запиту (без імені) надсилати Voyage / MongoDB. «Ні» → варіант (в).
2. **Ключ:** безкоштовний обліковий запис MongoDB Atlas → AI Model APIs → ключ Voyage → у `.env` сервера. Гроші: $0 у межах 200 млн токенів (чи попросять картку — (?)).
3. **20–30 хвилин** на перевірку тестових запитів.
4. Лише для (в) — скільки RAM вільно на VPS.

## 6. Словничок

- **Ембединг (вектор)** — список чисел, що описує зміст тексту.
- **Вимірність** — скільки чисел у векторі (384, 768, 1024…).
- **Косинусна близькість** — наскільки два вектори «дивляться в один бік», від −1 до 1.
- **Токен** — шматок слова; ним модель міряє текст, а постачальник — рахунок.
- **BM25** — класична формула порядку результатів за словами.
- **Лематизація / стемінг** — звести слово до словникової форми / обрізати закінчення.
- **doc2query** — LLM дописує до документа питання, якими його шукатимуть (наші «ключі»).
- **HyDE** — LLM вигадує відповідь на запит, а шукають уже за нею.
- **Розріджений вектор (SPLADE)** — вага для кожного слова словника, майже всі нулі.
- **Гібридний пошук / RRF** — злиття кількох списків результатів за місцями в них.
- **Переранжування (rerank)** — точніша модель пересортовує перших кандидатів.
- **RAG** — знайти фрагменти й дати LLM відповісти на їх основі.
- **Векторна база** — сховище з індексом для пошуку найближчих серед мільйонів векторів.
- **MTEB / MMTEB** — загальновизнаний набір тестів якості ембедингів (MMTEB — багатомовний).
- **ONNX / квантизація** — формат моделі для запуску без PyTorch / ваги меншими числами (int8, q4): файл у 4–8 разів менший, якість трохи нижча.
