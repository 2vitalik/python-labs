## Коротко

- **GitHub для цих лаб — оверкіл.** Лаба — один файл і одна-три здачі; усе, що дав би git, сайт дає сам і зручніше: знімок на момент здачі, історію версій, «що змінилось», час проти дедлайну, автора. Поле GitHub у профілі ods лишити необовʼязковим, здачу — файлом на сайт.
- **Перевірка — чотири шари, кожен дешевший для тебе за попередній**: сайт сам (секунди) → локальний перезапуск (хвилини на весь потік, без твоєї участі) → твоє око (1–2 хвилини на роботу) → захист. Розуміння перевіряє лише останній; три перші прибирають усе, що можна порахувати.
- **Сигнали — не вироки**: час роботи, кількість версій, однакові висновки сайт показує як привід для питання на захисті, а не як штраф ([T193](T193-C--ods-lab-ai.md)).

## GitHub чи сайт

| Що дає git | Як це є на сайті |
|:--|:--|
| незмінний знімок на момент здачі | кожне завантаження — окрема версія: оригінал байт у байт, його sha256, час сервера |
| історія | список версій; попередні не затираються |
| «що змінилось після зауваження» | клітинки, змінені між двома версіями, підсвічено; `git diff` на `.ipynb` — це JSON із картинками в base64, без окремих інструментів його не прочитати |
| дата — доказ дедлайну | час завантаження ставить сервер; дату коміту студент ставить сам |
| авторство | вхід поштою NURE |
| доступ викладача | не треба просити доступ до пʼятдесяти репозиторіїв і ловити «приватний» та «не той бранч» |
| копія поза компʼютером студента | файл у базі сайту; у студента лишається свій |

Чого git додав би понад це: навичку (вона є в курсі Python) і публічне портфоліо (ноутбук із персональним варіантом — слабке портфоліо).

Чого коштував би: з Colab у GitHub — окремий дозвіл Colab на репозиторії й ручний «Зберегти копію в GitHub» після кожної правки; з marimo — усе руками; підтримка «не запушилось» лягла б на тебе. На лабу припадає одна-три здачі — історії комітів там нема з чого складатися.

Де git лишається на місці: курс Python — там проєкт на багато файлів і десятки комітів, а журнал комітів сам є фактом для дедлайну.

Пропозиція: [T353](../../platform/.t/T353-Q--shared-to-core-choices.md) Q2 — «a»: поле GitHub у профілі ods лишається, ніхто його не вимагає.

## Чотири шари перевірки

| Шар | Хто | Що ловить | Скільки коштує |
|:--|:--|:--|:--|
| 1. Завантаження | сайт | числа ✅ / ❌ з назвою типової помилки; чи всі кроки зроблено; графіки; висновки; зірочки; чи ноутбук виконано згори донизу; підказка рівня | секунди, без тебе |
| 2. Перезапуск | `bin/nbrun` на твоєму ноутбуці | числа у файлі справжні — виходять із коду студента, а не вписані руками; виводи для marimo, де файл їх не несе | хвилини на потік, без тебе |
| 3. Око | ти | якість висновків і графіків: режим «висновки» збирає їх підряд | 1–2 хвилини на роботу, ← → між студентами |
| 4. Захист | ти й студент | розуміння | як і було; питання з картки — на тій самій сторінці |

Навіщо шар 2, якщо є шар 1. Коди самоперевірки в картці не розкривають відповідь, але її можна підібрати: перебрати числа, доки `check` не скаже ✅. Рядок відповідей і виводи у файлі теж можна дописати руками. Перезапуск показує, чи ці числа дає код. Для оцінки він не обовʼязковий — це страховка й привід для питання.

Порядок на тиждень: студенти здають файли → перед парою `bin/nbrun <лаба>` → «Результати» лаби: «де помиляються» підказує, що пояснити на ПЗ → перевірка робіт підряд → захисти.

## Що сайт показує як сигнал

- **Час роботи** — перший і останній запуск клітинок із файла Colab: «десять хвилин» проти «чотири вечори».
- **Версії** — скільки разів і коли здавали; що змінилось між ними.
- **Перезапуск не збігся** — число у файлі не те, що дає код.
- **Рівень роботи проти наміру** — зробив на 16, а захищатись не збирається: варто нагадати.

Жоден із них не міняє балів сам.

Перші три я б робив наступними: вони закривають щоденні незручності, решта — після перших захистів через сайт.
