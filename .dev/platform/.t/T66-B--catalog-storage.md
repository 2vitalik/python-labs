# T66 · Зберігання каталогу: БД, файли чи гібрид

`2026-08-04` · 🧠 brainstorm

Контекст:
- рамки раунду — [T65](../../.rounds/.t/T65-R--catalog-round-readback.md): ти редагуєш ігри й завдання через веб, студенти бачать перелік;
- наявне: Mongo + Beanie, колекції `users`+`history`, аудит через `record()` ([T57](T57-B--history-storage.md)); чернетки — `data/wiki/` (17 ігор, 6 зон); корпус цін — `data/v3/` (2130 рядків);
- ескіз колекцій уже передбачав `tasks` як довідник у Mongo — [T59](T59-C--data-model-sketch.md); питання «wiki: чернетка чи джерело правди» свідомо відкладалось ([T52](../../.t/T52-Q--kb-questions.md) Q5c).

## Що зберігаємо

Дві сутності-довідники: **гра** (slug, назва, іконка, клас, осі, опис-markdown, статус) і **завдання** (slug, назва, опис, дім зона/підзона, теги, застосовність до ігор, ціна, повторюваність, варіанти-сімʼя, статус). Обсяг смішний для БД: сотні документів, десятки КБ. Тому питання не «потягне чи ні», а **де живе правда і як тобі зручно правити**.

## Варіант A — Mongo як єдине джерело правди

Колекції `games` і `tasks`; wiki → одноразовий сид; далі всі правки — веб-адмінка.

- ➕ Послідовно з усім, що вже є: той самий Beanie, той самий `record()` — повний аудит правок задарма; студентські сутності майбутнього (свої ігри, пропозиції) — теж документи поруч.
- ➕ Веб-CRUD — саме те, що ти просив; правка ціни = два кліки, видно одразу.
- ➕ Майбутні звʼязки (звіт → task_id, лічильники «брали/зарахували», рекалібрація цін) живуть у тій самій базі — жодних мостів.
- ➖ Контент випадає з git: нема diff-ревізії правок, бекап — лише mongodump; мені (агенту) масово правити картки через адмінку — незручно.
- ➖ Довгі markdown-описи ігор у веб-textarea — можливо, але бідніше, ніж в IDE.

## Варіант B — content-as-code: каталог у git

Канонічний каталог — YAML/MD-файли в `data/catalog/`; app читає їх (при старті чи на льоту); правки — в IDE/через мене, комітяться.

- ➕ Git-версіонування задарма: історія, diff, відкат; я правлю контент цілими пачками однією сесією.
- ➕ wiki і каталог поруч, один світ файлів.
- ➖ **Веб-редагування нема** — а ти його явно просив; правка ціни = правка файла + деплой/перечитування.
- ➖ Студентські штуки потім (свої ігри, пропозиції) все одно підуть у Mongo → одразу дві системи зберігання і міст між ними.
- ➖ Лічильники/статистика на картці — знову в БД: правда розповзається.

## Варіант C — гібрид: правда в Mongo, знімок у git (рекомендую)

A + експортний місток: команда `export` скидає весь каталог у YAML (`data/catalog/`) — рівний, git-даффабельний знімок; `import` вантажить YAML назад (upsert по slug).

- ➕ Все з A (веб-CRUD, аудит, звʼязки) + git-знімок: бекап, diff між експортами, ревізія «що ми наредагували за місяць».
- ➕ **Сид = перший import**: я генерую стартовий YAML з wiki-ядра — тим самим механізмом, який далі служить для масових правок (я правлю YAML → import) і перенесення між середовищами (дев → прод).
- ➕ Формат YAML — один в один поля моделі, нічого не вигадуємо.
- ➖ Потрібна дисципліна «джерело — Mongo, git — знімок» (експорт — жестом, не автоматично); конфлікт «правив і в базі, і в YAML» вирішується просто: import перетирає, історія в `history` лишається.

## Доля wiki після сиду

- Пропозиція: wiki лишається **чернеткою/лором** — місце, де визріває новий контент і живуть довгі «Можливості» й «Сире»; каталог — оперативна вітрина з цінами. Дозріло у wiki → перенеслось у каталог (мною). Це продовження ролі, зафіксованої в [T54](../../.rounds/.t/T54-R--kb-round-decisions.md) (Q5c: «wiki стартує як чернетка»).
- Альтернатива — wiki поступово віддає все каталогу і застигає архівом; вирішувати не зараз, практика покаже.

## Суміжні мікрорішення (пропоную без окремого брейншторму)

- **Зони/підзони — константа в коді** (`zones.py` дзеркалить `data/wiki/tasks/_map.md`), не колекція: список закритий і рідко змінюваний ([T33](../../tasks/.t/T33-B--task-taxonomy.md)), зміна таксономії = свідомий акт у git. Теги — вільні рядки на картках.
- **Ціна — пара `coin` (тип) + `amount` (кількість)**: довідкове поле показу; жодної монетної математики у v1 — модель обміну лишається за [grading](../../grading/README.md) ([T08](../../grading/.t/T08-Q--grading-open-questions.md) відкритий) — зміниться модель, поле переживе.
- **Видалення нема — є `archived`**: справжній delete руйнує майбутні посилання (звіти студентів на task_id); архівне зникає з вітрини, лишається в базі.
