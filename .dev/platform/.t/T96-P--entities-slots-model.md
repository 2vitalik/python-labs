# T96 · Сутності, слоти, таблиця взаємодій — модель v1

`2026-08-17` · 💡 proposal · сесія механік; аналітика — [T95](../../games/.t/T95-B--mechanics-deep-dive.md), рішення — [T97](../../games/.t/T97-Q--mechanics-session-questions.md)

Принцип: жодної нової архітектури — все лягає в наявні Game/Part/Claim ([T92](T92-Q--naming-urls.md)) тими самими прийомами, що вікна й меню.

## 1. Сутності = `Part kind="entity"`

- Поля ті самі: `title` («Ворожий танк»), `description`, `screenshots` (скриншот/gif сутності — обовʼязковість доказів уже в правилах), `order`; нове маленьке поле **`role`** зі словника `player · enemy · object · pickup · static` — для іконки, групування і майбутніх підказок (не впливає на монетки).
- Заявки механік чіпляються як завжди: `Claim.part = <entity id>` («Ворожий танк реалізує `random-walk`»). Заявки рівня гри лишаються для того, що не привʼязане до сутності (`impassable-cells`, `destroy-all-enemies`).
- Тип-картки (як у вікон) сутність **не має**: каталог описує механіки, а не «типи танків»; сутність — чисто студентська річ, тому й авто-заявки при створенні нема.
- UI: секція «Сутності» в `/my/game` (картки як вікна: назва + role + скриншоти + чіпи заявок + пікер) і на паспорті. Компоненти вже є (`ShotStrip`/`ClaimRow`/`ClaimPicker`) — переважно перевикористання `WindowCard`.

## 2. Слоти параметрів (рівень 1)

- Картка каталогу: нове поле **`Task.slots`** — список `{key, label, type: int|choice|bool|text, options?, unit?, required?}` (порожній список = картка рівня 0; таких більшість — назавжди, і це ок).
- Заявка: нове поле **`Claim.params`** — маленький словник `{key: value}`; форма заявки рендерить слоти картки як 1–3 інпути; валідація по типах на бекенді.
- Паспорт/редактор: параметри показуються в чіпі заявки — `spawn-schedule · кожні 20 тіків · макс 4`.
- YAML-канал: слоти в `tasks.yaml` — через dict-fallback картки (як багаторядкові описи), граматику рядка `taskline.py` не чіпаємо.
- Стартові три картки-приклади (T86 Q3a): після «ок» — топ-20 (move/combat/spawn/state) чернетками.

```yaml
spawn-schedule:
  slots:
    - { key: every, label: 'Кожні', type: int, unit: 'тіків', required: true }
    - { key: max_alive, label: 'Макс. на полі', type: int }
blast-wave:
  slots:
    - { key: radius, label: 'Радіус', type: int, unit: 'клітин', required: true }
hp-damage:
  slots:
    - { key: hp, label: 'HP', type: int, required: true }
    - { key: who, label: 'Кого', type: text }
```

- Межа (з [T95](../../games/.t/T95-B--mechanics-deep-dive.md)): слот = число/дрібний вибір екземпляра; зміна суті/ціни — дитина сімʼї, не слот.

## 3. Таблиця взаємодій (рівень 2)

- Нова маленька модель **`Interaction`** (колекція `interactions`): `game · a` (Part id) `· b` (Part id) `· effects: list[dict] · note`; окремі документи — точна history по рядку і дрібні форми, як усюди.
- **Словник наслідків** — константа в коді (розширюємо ми): `disappear_a · disappear_b · disappear_both · block · push · pickup · damage{n} · transform{into: part} · teleport · spawn{part} · score{n} · custom{text}`; наслідків у рядку може бути кілька.
- UI: секція «Взаємодії» в `/my/game` — рядок = два селекти сутностей + чекбокси наслідків (з міні-полями для n/цілі) + нотатка; на паспорті — таблиця як у [T95](../../games/.t/T95-B--mechanics-deep-dive.md).
- Монетки: картка `interaction-table` заявляється раз на гру, рядки — дані (якщо в [T97](../../games/.t/T97-Q--mechanics-session-questions.md) Q3 не вирішимо інакше).

## 4. Порядок реалізації (кожен крок — окрема дрібна задача)

1. **E1 — сутності**: `kind="entity"` + `role`, секції в редакторі й паспорті; смоук.
2. **E2 — слоти**: `Task.slots` + `Claim.params` + форма + чіпи з параметрами; слоти на 3 картках-прикладах.
3. **E3 — таблиця взаємодій**: модель + UI + паспорт.
4. **E4 — топ-20 слотів** чернетками через YAML → твоя ревізія.

E1 можна робити одразу після відповідей [T97](../../games/.t/T97-Q--mechanics-session-questions.md); E2–E3 незалежні одна від одної.
