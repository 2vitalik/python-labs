## Поле гравців (async Mongo у Python)

- **Голий драйвер (PyMongo Async).** Класичний Motor у 2025 MongoDB оголосила застарілим — офіційний шлях тепер асинхронний API самого PyMongo. Працюєш зі словниками: максимум контролю, нуль магії, але схема/валідація/типізація — руками (Pydantic окремим шаром). Для однієї колекції — терпимо; на десятках сутностей курсу (завдання, заявки, монетки, зауваження…) розповзається в клей.
- **Beanie** — тонкий ODM поверх Pydantic (з версії 2.x — на PyMongo Async): документ = Pydantic-клас, валідація/типи/дефолти з коробки; та сама модель працює як FastAPI-схема відповіді. Найактивніший з Mongo-ODM.
- **ODMantic** — та сама ідея, але розвивається уривками (довгі паузи без релізів), менша екосистема.
- **MongoEngine** — старий, синхронний, Django-стайл, без Pydantic — у async-FastAPI чужорідне тіло.

## Чому Beanie тут — так

- Критерій «лаконічний зрозумілий код»: `class User(Document)` з типами полів — самодокументація; запити читаються природно: `await User.find_one(User.email == email)`.
- Тонкий шар, не «ORM-вʼязниця»: будь-де можна впасти до сирого запиту чи aggregation pipeline — Beanie Mongo не ховає.
- Повертає Mongo дисципліну схеми: єдине джерело правди про структуру документа — модель у коді.
- Рішення легко оборотне: у мікро-MVP ODM торкається одного файлу (модель User); заміна на будь-яку альтернативу — година роботи. Влипнути нема куди.

## Вердикт

- Для звʼязки FastAPI + Pydantic + Mongo — так, Beanie найкращий практичний вибір. Єдина чесна альтернатива — голий PyMongo Async + Pydantic руками: ті самі гарантії, але більше самописного клею.
