## Рішення: так, батько-діти — і чому це правильно

Вкладені `variants` були «недо-завданнями»: без опису, без статусу, без історії правок, з окремим UI. Поле `parent` знімає все одним махом:
- **одна модель** — дитина має все, що має будь-яке завдання (опис, теги, статус, history, ✏️-форму);
- **звіти майбутнього** посилаються на будь-яке завдання однаково — окремої логіки «зарахувати варіант» не існує;
- **UI рекурсивний** — та сама картка рендерить дітей усередині сімʼї;
- обмеження: **один рівень глибини** (батько не може сам мати батька) — валідація в API; глибші дерева каталогу не потрібні, це вже була б ієрархія зон.

Що таке сімʼя тепер: звичайна картка, на яку показує `parent` інших карток. Її власна монетка — досі довідкова (UI показує діапазон дітей «📎‥🥇»).

## YAML v2 (за твоїм синтаксисом із [T78](T78-Q--catalog-ui2.md) Q3, реалізовано)

`data/catalog/tasks.yaml` — дерево зона → підзона → рядки; позиція рядка = order:

```yaml
entities:
  move:
  - move-by-input: 🥉 Рух за вводом — 4 напрямки; ввід керує переміщенням аватара.
    children:
    - move-4dir: 🥉 4 напрямки
    - chase-bfs: 🥇 Пошук шляху BFS/A* ⭐
  - inertia-slide: 🥉 Інерція [inertia] ✍️ — Ковзання до упору.
```

Граматика рядка (`taskline.py`): `🥉[×N] Назва [ігри, комою] ⭐ #тег 🔁[N] ✍️ — опис`; без маркера статусу = **active**, ✍️ = чернетка, 🗄️ = архів, ⭐ = тег algo, 🔁 = без ліміту / 🔁N = до N. Багаторядковий опис — fallback у повну словникову форму (парсер розрізняє за типом). Раундтрип перевірено: export → import = «без змін 185».
