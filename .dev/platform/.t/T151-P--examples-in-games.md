# T151 · Приклади ігрових ситуацій — у картках ігор

`2026-09-28` · 💡 proposal · запит Vitalik у чаті: «щоб ці приклади були прив'язані до ігор, щоб ця інформація була відповідно в іграх. Що для цього треба зробити?» · вибори — [T152](T152-Q--examples-in-games-choices.md)

## 1. Як зараз

- Пʼять прикладів (23 поля-клітинки) — розкривашки `<details>` у розділі `## Приклади ігрових ситуацій {#examples}` сторінки методички `game`: файл `data/guide/game.md` → Mongo `guide` (rev 0, як засіяно; [T128](T128--guide-editor-v1/report.md)).
- Ігри — окрема колекція `games` (`models/base_game.py`), знімок — `data/catalog/games.yaml`. Звʼязку з прикладами нема: це просто текст із назвою гри в заголовку розкривашки.
- Усі пʼять ігор у каталозі є, `active`:

| Розкривашка | slug гри |
|---|---|
| 🧩 Лабіринт | `maze` |
| 🔵 New Ball Game | `new-ball-game` |
| 🪜 Lode Runner | `lode-runner` |
| 💣 Mined-Out | `mined-out` |
| 🧊 Inertia | `inertia` |

- Сторінка гри `/games/<slug>` малює опис простим `marked` (`Md.vue`): блок ` ```field ` там вийде сірим кодом, а не сіткою. Сітку й виноски вміє лише рендер методички (`md.js` + `GuideText.vue`).
- Доступ: `/games/<slug>` і картки каталогу — лише адміну (T116 Q13), а текст `/games` після відкриття методички бачитимуть усі. Перенос «лише на сторінку гри» забрав би приклади у студентів.

## 2. Що зробити

1. **Поле в грі.** `BaseGame.examples: str = ""` (markdown) + те саме в `GameIn` і `api()`. Знімок `games.yaml` підхопить поле сам: `dump()` у `catalog_io.py` загальний.
2. **Показ на сторінці гри.** Під описом — розділ «Приклади ігрових ситуацій», рендер через `GuideText` (сітка, виноски, якорі). Опис гри теж перевести з `Md` на `GuideText`: один рендер на сторінку.
3. **Показ на `/games`.** Компонент `GameExamples.vue`: заголовок `#examples`, вступний абзац і розкривашка на кожну гру з непорожнім `examples` (іконка й назва — з гри). Стоїть під текстом методички, видно всім, хто бачить текст. Для студента сторінка виглядає як зараз, тільки дані йдуть з ігор.
4. **Редагування.** У `BaseGameForm.vue` — textarea «Приклади» і превʼю під нею тим самим `GuideText`: без превʼю сітку доводиться правити наосліп. Історія правок уже пишеться: `record()` у `PUT /api/games/{id}`.
5. **Перенос даних — скриптом по базі, не по файлах.** Разовий `app/api/move_examples.py`: бере `body` сторінки `game` з Mongo, вирізає пʼять `<details>` за таблицею вище, кладе кожен у `games.examples`, сторінку методички зберігає через `save()` з нотаткою (правка лягає в історію, відкат працює). Розділ `#examples` з тексту зникає цілком — його малює п. 3. Скрипт нічого не робить, якщо розкривашок у тексті вже нема, тож повторний запуск безпечний.
6. **Знімки.** Після скрипта — `guide_io.py export` і `catalog_io.py export`: `game.md` коротшає з 432 до ~45 рядків, у `games.yaml` зʼявляється `examples`. Щоб поля в YAML читались, багаторядкові рядки писати literal-блоком `|` (зараз PyYAML згортає їх у лапки з порожнім рядком між кожними двома) — 5 рядків у `catalog_io.py`, разовий великий diff у `games.yaml`.
7. **Сервер.** Там своя база, тож після деплою запустити той самий скрипт. Після обох запусків скрипт видалити.
8. **Тести й доки.** `smoke_games.py` — поле `examples` у створенні, правці й видачі; `smoke_guide.py` — без змін. `data/guide/README.md` (конвенція «Поле-клітинки» посилається на `game.md`), `data/catalog/README.md`, README вузла, CHANGELOG.

| Частина | Рядків |
|---|---|
| модель, роут | ~6 |

Разом **S–M**, одна сесія. Нових залежностей нема.

## 4. Чого не роблю

- Структури прикладу (легенда, кадри, підписи окремими полями) — лишається один markdown-текст на гру. Розкладати на поля варто, коли зʼявиться редактор поля або приклади почнуть використовуватись окремо від сторінки.
- `/method` (уся методичка однією сторінкою): прикладів там не буде, у розділі «Ігри» лишиться посилання на `/games#examples`. Додати блок і туди — окремим кроком, якщо захочеш.
