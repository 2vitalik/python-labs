# T271 · ТЗ: еталони й демо-ігри під модель v3

Робочий документ задачі — спільна частина ТЗ для тих, хто переписує `data/catalog/templates/*.yaml` (еталонні описи 17 базових ігор) і `data/demo/*.yaml` (ігри демо-студентів) після зміни каталогу й моделі ([T270](../../../games/.t/T270-P--game-desc-v3-design.md) §6, §8, §9).

## Що змінилось

- У кожної картки каталогу тепер є **тип** (`kind`), і він каже, де картці місце: `rule` — на правилі (`rules[].claims`), `mechanic` — на сутності (`entities[].claims`), `element` — на вікні (`windows[].claims`), `field` — про поле (верхній `claims`, сама ляже на поле), `level` — на рівні (`levels[].claims`) або у верхньому `claims`, `game` — верхній `claims`. Типи `role`, `stat`, `fieldopt`, `window` **не пишуться в `claims` взагалі**: вони обираються самим описом — роллю сутності, її параметром, властивістю поля, типом вікна — і заявляються самі.
- Тип картки: у `data/catalog/tasks.yaml` — `@kind` у рядку картки (`@rule(contact?free>push)` — картка-правило з заготовкою: слова, з яких складається її правило; `@(all_gone>win)` — те саме з типом підзони) або `kind:` у словниковому записі; без позначки — тип підзони (`app/api/zones.py`, третій елемент підзони). Швидко глянути тип і заготовку будь-якої картки: `cd app/api && uv run python -c "import yaml,sys; from catalog_io import task_rows; from zones import default_kind; [print(r['slug'], r.get('kind') or default_kind(r['zone'], r['subzone'], r.get('tags', [])), r.get('rule') or '', r.get('status')) for r in task_rows() if r['slug'] in sys.argv[1:]]" <slug> <slug>…`
- 34 картки влито в інші й заархівовано — мапа `.dev/platform/.t/T271--game-desc-v3/catalog/merged.yaml` (`стара: нова`). Стару картку в `claims` треба замінити тим, чим вона стала:
  - стала **параметром** (`stat-*`: `hp-damage`, `shoot-cooldown`, `timed-despawn`, `speed-per-type`, `inventory-limit`…) → рядок у `stats` відповідної сутності (`{key: hp, value: "4"}`), з `claims` прибрати;
  - стала **типом сутності** (`spawner-entity → role-spawner`) → `role: spawner` у сутності, з `claims` прибрати;
  - стала **властивістю поля** (`keyboard-controls → control-direct`, `cell-click → control-click-cell`, `gravity-fall → gravity-down`, `swipe-all-shift → control-swipe-all`, `height-levels → grid-layers`, а також `wrap-edges`) → значення в `field` (`control: [direct, click-cell]`, `gravity: down`, `topology: layers`, `wrap: true`), з `claims` прибрати;
  - стала **іншою карткою** → новий slug на місці, яке каже її тип.
- Властивості поля: `time` і `control` — списки; `gravity: none` не пишеться (нема значення = нема гравітації); варіанти кожної властивості — картки зони `field` у `tasks.yaml` (`opt: властивість:значення`).
- Параметри сутності: ключі каталогу — картки `stat-*` (`opt` = ключ: `hp`, `lives`, `speed`, `damage`, `armor`, `range`, `capacity`, `cooldown`, `value`, `count`, `duration`, `size`, `ammo`, `cost`, `vision`, `side`, `energy`, `rank`); одиницю дає картка, якщо в неї вона є (свою одиницю можна лише там, де в картки одиниці нема, як у `cost`). Якщо число — про інше або в іншій одиниці, ніж у картки (швидкість у %, час у секундах), — це **свій** параметр: `{key: "швидкість, %", value: "80"}` — ключ своїми словами, одиниця в `unit` за бажанням.
- Нове: `entities[].icon` (емодзі, коли іконка ролі погано пасує: 👻 привид, 📦 ящик, 🍒 фрукт), секція **`levels`**, `rules[].claims`.
- Формат і приклад — `data/catalog/templates/README.md` (оновлений), слова правил — `app/api/models/vocab.py` (шаблони речень змінились, імена слів і аргументів — ні).

## Як переписати один файл

1. Поле: прибрати `gravity: none`; `time`, `control` — списками; що раніше було карткою, а тепер властивість, — у властивості.
2. Кожну картку з усіх `claims` перевірити на тип і покласти на своє місце. Картка `rule` — на **те правило, яке каже її поведінку**. Заготовка картки — лише підказка редактора (нею відкривається нове правило і за нею підказується картка): ні сервер, ні `validate.py` її не звіряють. Тому правило **не переписується під заготовку** — вірність грі важливіша: міна, на яку став, — це `enter → поразка`, і «Смерть від дотику» сідає саме на таке правило; параметрів і правил заради заготовки не вигадувати. Якщо правила про цю поведінку в файлі нема — дописати його (воно й так має бути в описі гри), а не лишати картку без правила. Одна картка — на одному правилі, найпоказовішому.
3. Правила без картки — нормально: не кожне речення є карткою.
4. Додати `levels`: 1–3 записи про те, як у класичній грі влаштовані рівні — `title`, `mode` (`hand` · `file` · `generated` · `endless`), `count`, `size`, за потреби `stats` (свої параметри рівня: `{key: "ворогів", value: "20"}`), `description`, властивості поля, що на цьому рівні інші, і `claims` — картки типу `level` (формат, прогресія, генерація…), які справді є в класичній версії. Розмір, що різний на рівнях, — у рівнях, а в `field.size` — типовий або нічого.
5. Обсяг той самий: 4–10 сутностей, 8–20 правил, 3–6 вікон; це стартове меню студента, не енциклопедія. Назви сутностей і вікон **не міняти** (на них спираються демо-ігри), зміст описів не переписувати без потреби.
6. Перевірка, з `app/api` (у кожного агента — **своя** скретч-база, імʼя закінчується на `_smoke`):
   - `uv run python -I ../../data/catalog/templates/validate.py ../../data/catalog/templates/<файл>.yaml` → `ok`;
   - `DB_NAME=python_labs_<твоє імʼя>_smoke uv run python "/private/tmp/claude-505/-Users-v6u-Main-Dropbox-Dev-Dev-v4-Nure-python-labs/ce0b9770-b7a9-4bc9-b98f-eaa4cf0f5170/scratchpad/pour_check.py" <slug> <slug>…` → для кожного `ok`, `skipped []`, `drafts []`, `second pour adds {}`.
   - наприкінці прибрати свою базу: `mongosh --quiet <імʼя бази> --eval 'db.dropDatabase()'`.

## Демо-ігри `data/demo/*.yaml`

Формат — як в еталона плюс своє ([README](../../../../data/demo/README.md)): `student`, `game`, `etalon: true` (спершу ллється еталон основи, потім файл), `shots`, а в картках — `note`, `link`, `status`, `verdict`. Переписати за тими самими кроками, і ще:

- Еталони вже переписані: якщо в демо-грі `etalon: true`, те, що еталон тепер несе сам (рівні, картки на своїх правилах), у файлі не повторювати; правило з файла, яке збігається з еталонним слово в слово, зливається з ним — тож **картку на еталонне правило** можна повісити, повторивши це правило у файлі з `claims`.
- Вердикти (`status`, `verdict`), нотатки й лінки переїжджають разом з карткою на її нове місце. Якщо картка стала параметром, типом чи властивістю поля — її вердикт зникає (авто-заявку оцінюють окремо); скільки таких — сказати у звіті.
- Задум кожної гри з таблиці README лишається: `sketch` — навмисно сира (чернетки без місця, картки без параметрів — тепер це картки-правила без правила і картка вікна без вікна), `tanks` — максимум усього, `rogue` — своя основа без еталона, усі зони каталогу. Додати в кожну «живу» гру секцію `levels` (у `tanks` — 3–4 записи з параметрами й скриншотом-мапою через `shots`, у `rogue` — згенеровані підземелля), щоб нова секція була показана.
- Перевірка, з `app/api`: `DB_NAME=python_labs_<твоє імʼя>_smoke uv run python catalog_io.py import`, далі `DB_NAME=python_labs_<твоє імʼя>_smoke FAKE_USER_EMAIL=dev@nure.ua UPLOADS_DIR=<своя тека в скретчпаді> uv run python demo_io.py seed <імʼя> <імʼя>…` — у виводі не має бути «пропущено» (крім навмисних чернеток `sketch` — вони не пропускаються, а лягають без місця); наприкінці базу прибрати. Дев-базу `python_labs` не чіпати.

## Правила

- Чіпати лише свої файли зі списку в ТЗ; не чіпати код, каталог (`tasks.yaml`, `aliases.yaml`), `.dev/`, git. Якщо картки, якої бракує, в каталозі нема — не вигадувати slug, а написати про це у звіті.
- `uv` запускати лише з `app/api`; перед першим запуском — `echo $UV_PROJECT_ENVIRONMENT` має показати `/Users/v6u/.venvs/python-labs`.
- Звіт: по кожному файлу — що переїхало куди (коротко), які правила дописано, які рівні, вивід обох перевірок; окремо — чого бракує каталогу чи словнику.
