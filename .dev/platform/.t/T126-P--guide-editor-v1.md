## 2. Що зберігаємо

- Колекція **`guide`**, документ = сторінка: `{slug, title, body (markdown без першого `#`), updated_at, updated_by}`. Slug-и й порядок — як зараз у `guide.js`/`data/guide/`.
- **Правка = вся сторінка**, навіть коли редагуєш один `##`: фронт вирізає розділ (від його заголовка до наступного того ж або вищого рівня), даєш текст, при збереженні вклеює назад і шле `PUT /api/guide/{slug}` з повним `body`. Якорі `{#id}`, рендер, `/method`, зміст — без змін; ніякої структури «розділ = документ», яка б зламала посилання і порядок.
- **Історія** — той самий `record()` → `history`: `{coll: "guide", doc_id, actor, at, changes: {body: {old, new}}}` + нове поле `note` (один рядок «що змінив», необовʼязково). Тексти ≤ 20 КБ, 200 правок за семестр ≈ 8 МБ — прийнятно; diff рахуємо при показі, не зберігаємо.
- Файли `data/guide/*.md` — **seed і експорт** (`guide_io.py` за зразком `catalog_io.py`: `import` при першому запуску, `export` — дамп для git/читання). Правда — Mongo. Правка файла після імпорту на сайт не потрапляє (як у каталозі).

## 3. Як редагуємо (п. 32)

- Адмін бачить «✏️» біля `#` (вся сторінка), кожного `##` і `###` (Md-рендер уже вміє кнопки на заголовках — 🔗). Клік → під заголовком розкривається **інлайн-редактор**: `textarea` (авто-висота, моноширинний) + живе превʼю праворуч/знизу (`GuideText`, той самий рендер, що на сайті) + рядок «Що змінив» + «Зберегти / Скасувати». Один редактор на сторінці за раз; захист від втрати змін — `useForm()` з профілю (`dirty`, попередження при переході).
- Зберегти → `PUT` → сторінка перерендерилась, «Оновлено» оновилось. Конфлікт двох вкладок: `PUT` несе `updated_at`, який бачив; не збігся → 409 «сторінку вже змінили, перезавантаж» (ти один, але Dropbox-подібних сюрпризів не хочеться).
- Вся сторінка — той самий редактор на `#`; окремий маршрут `/labs/1/edit` не потрібен.
- Обсяг: модель + `guide_io.py` + 2 роути (`GET` є, `PUT` + `GET history`) ≈ 80 рядків; `GuideEditor.vue` ≈ 90; кнопки ✏️ у рендері + вирізання/вклеювання розділу (`md.js`) ≈ 40. Разом **M** (~250 рядків).

## 4. Історія і показ змін (п. 33–34)

- `GET /api/guide/{slug}/history` → список правок: дата, хто, нотатка, `+N/−M` рядків.
- Сторінка `/method/history` (усі розділи разом, найновіші зверху) і та сама з фільтром `?slug=`; лінк «історія» біля «Оновлено» внизу сторінки (адмін).
- Показ: рядковий diff (LCS по рядках, ≈ 30 рядків JS, без бібліотеки) — зелені/червоні рядки, контекст ±2, «розгорнути все». Кнопка «Повернути цю версію» = нова правка зі старим `body` і нотаткою «відкат до дд.мм».
- Пізніше, якщо захочеться: diff по словах усередині зміненого рядка (є `diff`-бібліотека 10 КБ).

## 5. «Що змінилось» (п. 35)

Три рівні, сумісні між собою:
- **a) вручну** — як зараз: `changes.md` редагуєш тим самим редактором.
- **b) нотатка → чернетка** *(рекомендую одразу)*: збереження з непорожньою нотаткою додає рядок `- **дата** — Розділ: нотатка` у **чернетку** (`changes.draft`, окремий документ, студентам не видно). На `/changes` адмін бачить чернетку над текстом і переносить рядки в публічний список (кнопка «↑ у публічне» = вклеїти в `changes` body) або видаляє. Так журнал росте сам, а публікуєш ти.
- **c) модель** *(потім)*: кнопка «Скласти запис» біля правки → diff + контекст розділу йдуть у Claude, повертається рядок «для студентів» у стилі методички; ти правиш і публікуєш. Один виклик API на кнопку, без автопублікації.

## 6. Приклади ігрових ситуацій — поле з емодзі (п. 45)

**Чи однаково виглядає плоский текст.** Ні, не гарантовано:
- Емодзі — не моноширинні: Apple Color Emoji, Segoe UI Emoji (Windows), Noto Color Emoji (Android/Linux) мають різну ширину гліфа (≈ 1.2–2 «клітинки» моно-шрифту), а браузер підбирає їх по-гліфному через fallback — у `<pre>` рядки з різною кількістю емодзі зʼїжджають.
- Частина символів (⬜ ⬛ ◻️ ▪️ ⭐ ❤️ ✅) — «текстові» за замовчуванням: без `U+FE0F` на Windows/Linux малюються монохромно й вужче, на macOS — кольорово. Обʼєднані (ZWJ, тони шкіри) — один гліф, але кілька code points.
- Висновок: **як простий текст — лише для «приблизно так»**; для рівної сітки потрібен рендер клітинками.

**Пропозиція.** У Markdown — блок ` ```field ` з рядками поля; `GuideText` рендерить його компонентом **`Field.vue`**: кожен рядок ділиться на графеми (`Intl.Segmenter`, є в усіх сучасних браузерах), кожна графема — `span` фіксованого розміру (`1.6em × 1.6em`, `display: grid`, центрування), порожня клітинка — `.` або пробіл. Однаково на всіх ОС, бо ширину задає CSS, а не шрифт; ≈ 20 рядків. Таблиця Markdown із емодзі — теж варіант, але громіздко писати й правити.

**v1** — приклади з Notion у розділ (`game.md` / `lab*.md`) у `<details><summary>Приклади ситуацій</summary>` з ` ```field `-блоками; правиш їх тим самим редактором (п. 3). **Потім** — міні-редактор поля: палітра емодзі, клік по клітинці. Обсяг v1: **S** (`Field.vue` + рендер ` ```field ` ≈ 40 рядків), контент — переніс із `data/v2/notion/`.
