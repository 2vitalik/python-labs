# T57 · Історичність даних: варіанти зберігання

- застосування у профілі — [T56](T56-P--profile-pages-design.md); майбутні колекції — [T59](T59-C--data-model-sketch.md).

## Варіанти «де зберігати»

- **a) Одна глобальна колекція** **`history`** (рекомендую): кожна зміна — окремий документ `{coll, doc_id, actor, at, changes}`.

  - Плюси: один хелпер на ~15 рядків обслуговує **всі** теперішні й майбутні колекції безкоштовно; сторінка «всі зміни» = один запит із сортуванням за датою; фільтр по студенту/колекції — тривіальний; основні документи лишаються чистими.

  - Мінуси: різнорідні записи в одній колекції — але в Mongo це норма, а форма запису в нас однакова для всіх.

- **b) Підколекція на кожну колекцію** (`users_history`, `reports_history`…): має сенс лише якщо історія різних сутностей має різну форму — не наш випадок; ціна — N колекцій, більше коду, «всі зміни разом» вимагає N запитів.

- **c) Вбудований масив в документі** (`user.history = [...]`): дані подорожують із документом, але документ росте без межі, глобальна сторінка змін стає болючою, кожен апдейт тягне весь хвіст. Відкидаю.

## Варіанти «що зберігати»

- **Дифф** (рекомендую): лише змінені поля `{field: {old, new}}` — прямо відповідає на питання «що змінилось», компактно, читається без обробки.
- **Повний знімок** документа при кожній зміні: простіше писати, але важко читати (щоб побачити зміну — диффити сусідні знімки) і роздуває базу. Відкидаю.
- Створення документа теж пишеться в історію (усі поля як `{old: null, new: …}`) — видно і появу студента (імпорт/перший вхід).

## Ескіз реалізації (варіант a + дифф)

```python
class Change(Document):
    coll: str            # "users", "reports", ...
    doc_id: PydanticObjectId
    actor: str           # email того, хто змінив (студент чи адмін)
    at: datetime
    changes: dict        # {"github": {"old": "...", "new": "..."}}

    class Settings:
        name = "history"
```

- Хелпер `record(doc, new_data, actor)`: порівняв поля → якщо є різниця, зберіг `Change` + застосував зміни. Викликається явно з PUT-роутів — жодних middleware і магії.
- `actor` природно розрізняє «студент сам» і «адмін за нього»; окремого поля не треба.
- Індекс `(coll, doc_id, at)` — миттєва історія конкретного документа.
