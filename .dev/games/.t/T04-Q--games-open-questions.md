**Q1 — Список ігор-прикладів.** Ти казав, що перелічиш ігри, які вже були в системі (і нові кандидати з YouTube/Steam). Накидай хоча б сирим списком — це база для каталогу і для розкладання на механіки.

> 

**Q2 — Python-курс: чи лишається клітинне поле обовʼязковим форматом?** Для ООП зрозуміло. А для Python:
- a) так, той самий формат «гра на клітинному полі» (рекомендую — порівнюваність і переиспользование каталогу завдань);
- b) клітинне поле — дефолт, але дозволені інші формати ігор/проєктів;
- c) для Python формат ширший (не тільки ігри).

> 

**Q3 — Консоль + GUI для Python.** У брейндампі ти вагався і схилявся до «хай буде і те, і те». Фіксуємо?
- a) так: лабораторні — консоль, курсовий — GUI, спільний двіжок (рекомендую — прямо тренує розділення логіки/виводу);
- b) консоль опційна, GUI обовʼязковий;
- c) ще думаєш.

> 

**Q4 — Генератор рандомних варіантів.** Що він генерує в ідеалі:
- a) специфікацію (набір механік/елементів + обмеження), студент реалізує з нуля (рекомендую);
- b) специфікацію + starter-код скелета під неї;
- c) поки не потрібен — це фіча «на потім».

> 

**Q5 — Своя гра студента.** Наскільки вільна: чи мусить бути на клітинному полі, хто затверджує, чи були прецеденти, які проблеми з ними виникали?

> 

**Q6 — GUI-технологія для Python.** Чим студенти малюють GUI: pygame, tkinter, PyQt, arcade, вільний вибір? Це впливає на каталог завдань (віконця, менюшки).
