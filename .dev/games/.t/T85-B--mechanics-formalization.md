# T85 · Формалізація механік: рівні формальності замість мови правил

- обʼєктний шар, на який це спирається, — [T83](../../reports/.t/T83-B--game-objects-model.md); питання — [T86](T86-Q--mechanics-questions.md).

## Рамка: питання не «яка схема YAML», а «скільки формальності купувати»

Кожен рівень формальності щось коштує (форми для студента, картки для тебе, UI для нас) і щось дає (чек-лісти, порівняння, наочність). Тому пропоную не одну схему, а **драбину рівнів** — і купувати формальність лише там, де вона окупається.

## Драбина

### Рівень 0 — картка + вільний текст (вже працює)

Механіка = заявлена картка каталогу + опис словами + gif. Каталог уже несе ~80 карток механік по підзонах (рух, бій, легальність, стан, взаємодія…).

- Плюси: нуль нової моделі; будь-яку унікальну механіку можна описати; це вже покриває «зникнення», «складні ситуації» — картками environment-death, timed-despawn, cell-transform тощо.
- Мінуси: не машинне — чек-ліст захисту і порівняння варіантів лише приблизні.

### Рівень 1 — картка + параметри екземпляра (пропоную як ціль семестру)

Заявка механіки на сутності несе маленький словник параметрів, **слоти яких визначає сама картка каталогу**: `move-by-input {напрямків: 4}` · `hp-damage {hp: 3}` · `spawn-schedule {кожні: 20 тіків}`. Слот = імʼя + тип (число/вибір/текст) + опційність, описується в картці; у формі студента це 1–3 маленькі поля, не YAML.

- Плюси: структура зʼявляється саме там, де вона дешева; чек-ліст захисту («перевір: 4 напрямки, hp=3») і різниця варіантів стають точними; форма лишається тривіальною.
- Мінуси: треба пройтись по картках і додати слоти — робиться поступово, спершу топ-20 (рух/бій/стан/спавн), решта живе на рівні 0. Це нормальний стан системи, а не перехідний.

### Рівень 2 — реляційні структури там, де природа даних — таблиця чи граф

Деякі речі в принципі не описуються полем на картці — вони **між** сутностями:

- **Таблиця взаємодій** «X × Y → наслідок» — картка interaction-table вже існує! UI: рядок = пара сутностей + наслідок зі словника: `зникає A` / `зникає B` / `зникають обидва` / `блокує` / `штовхає` / `бере в інвентар` / `шкода N` / `трансформація у Z` / `телепорт` / `інше (текст)`. Словник — checkbox-vocab, розширюваний тобою; **словник, не мова** — оце і є твій баланс. Покриває взаємодію не-гравець×не-гравець, зникнення при контакті, підбирання — левову частку «складних ситуацій» з [T82](../../.rounds/.t/T82-R--game-desc-braindump.md).
- **Граф переходів вікон** — вже в [T83](../../reports/.t/T83-B--game-objects-model.md), та сама ідея для UI.
- Кандидати пізніше: розклад хвиль (таблиця «хвиля → склад»), правила інвентаря (хто бере × що дає).

Кожна структура — окремий маленький UI; вводити по одній, коли назріє.

### Рівень 3 — мова правил (DSL: тригер → умова → ефект). НЕ робимо

- Це друга мова програмування: студент описує гру двічі (в коді і в DSL), а ти перевіряєш два артефакти замість одного.
- Унікальні механіки все одно не ляжуть у будь-яку мову — завжди лишиться «інше (текст)».
- Свідома межа системи: перевіряє гру захист і код, а опис — навігація і прайс, не виконувана специфікація. (Збігається з ризиком «не перетискати» в [T34](T34-P--game-spec-model.md).)

**Рекомендація: еволюція 0 → 1 → 2, без 3.** Старт семестру можливий на рівні 0 — драбина не блокує «Мою гру» v1.

## Як це покриває твої болі з T82

- Характеристики (життя, міцність, патрони) → слоти рівня 1 на картках стану (hp-damage, inventory, temporary-modes…).
- Зникнення → картки death-підзони (рівень 0) + наслідки в таблиці взаємодій (рівень 2).
- Взаємодія не-гравець×не-гравець → таблиця взаємодій: пара будь-яких сутностей, не лише гравця.
- Інвентар («хто може брати, як використовує, чи може ворог») → сімʼя inventory + слот «хто може» + рядки таблиці взаємодій.
- Нові класи (шахи, пазли) → вже в таксономії: легальність ходу, перевірка обмежень, суперник — підзони карток; додаткової формальності не просять.
- Старі 4 «варіанти» на сутність → це і були зародки слотів (поява/рух/взаємодія); рівень 1 — їх законне продовження, тільки слоти тепер визначає картка, а не жорстка четвірка.

## Складні фічі (редактор, магазин) — ієрархія вже є, нове не потрібно

- Механізм угрупування вже вирішений двічі: **підзони** (levels/editor існує: in-game-editor, editor-map-check, level-exchange) і **сімʼї батько-діти** ([T79](../../platform/.t/T79-C--family-v2.md)).
- Редактор рівнів: добудувати дітей/сусідів у підзоні editor — інструменти (олівець/прямокутник/лінія/заливка), undo/redo, палітра елементів, плейтест з редактора, перевірки прохідності.
- Магазин: сімʼя навколо shop-between-levels — вітрина, ціни, баланс, розпродажі/знижки, превʼю товару.
- Правило межі: фіча розрослась до ≥4 карток → сімʼя; сімʼя переросла батька → підзона. **Теги для групування не вводимо** (навігація по них слабка); теги лишаються вимірами (гра, клас, ⭐), як прийнято в [T70](../../.rounds/.t/T70-R--catalog-decisions.md).
- Анти-хаос каталогу: перед новою карткою — пошук по slug/назві; в адмінці підказка «схожі картки»; періодичний аудит дублів (можу ганяти я).
