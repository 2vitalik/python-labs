Контекст:

- «гра як композиція механік» — [T03](T03-C--grid-games-concept.md); таксономія тасків — [T33](../../tasks/.t/T33-B--task-taxonomy.md); каталог ігор — [T32](T32-C--grid-games-catalog.md).

## Ключова ідея: spec — не документ, а результат вибору тасків

Студент не пише YAML руками. Він у веб-каталозі обирає гру-основу і набирає таски — а система **збирає spec гри автоматично** з фрагментів, які несе кожен таск. Спека стає:

- **контрактом на захист** — чек-ліст «що має бути в грі і як я це перевіряю» генерується зі спеки;
- **описом варіанта** — два студенти з різним набором тасків мають формально різні ігри (перевірка «чи не однакові роботи» = порівняння спек);
- **входом генератора варіантів** ([T04](T04-Q--games-open-questions.md) Q4) — згенерувати рандомний варіант = насемплити фрагменти;
- людиночитаним експортом (YAML/MD) — за бажанням, як артефакт до звіту.

## Скелет спеки (пропозиція)

```yaml
meta:
  title: "Tanks by Petrenko"        # назва роботи студента
  base_game: battle-city            # гра-приклад з каталогу або custom
  course: oop-2026

field:
  size: [11, 5]                     # або dynamic
  topology: bounded                 # bounded | torus (карта-тор з pzpi-24)
  tick: turn-based                  # turn-based | timer(ms)

entities:                           # кожна сутність — набір обраних тасків-фрагментів
  player:
    symbols: {console: "▲", gui: "tank.png"}
    params: {hp: 3, ammo: 10, speed: 1}      # зона Сутності/Параметри
    moves: arrows-4                            # Сутності/Рух
    abilities: [shoot-forward, shoot-cooldown] # Сутності/Бій
  enemy-tank:
    count: {start: 2, wave: +1}                # Логіка/Хвилі та спавн
    ai: patrol-then-chase                      # тег algo, золота
    abilities: [shoot-on-sight]
  brick-wall: {passable: false, destructible: true}
  bonus-medkit: {on_pickup: "+1 hp", spawn: random-every-20-ticks}

interactions:                       # табличка «хто на кого як діє»
  - [projectile, brick-wall]: destroy-both
  - [projectile, player]: "-1 hp"
  - [player, bonus-medkit]: pickup

rules:
  win: [all-enemies-dead]           # Логіка/Перемога
  lose: [hp-zero, base-destroyed]   # Логіка/Поразка
  score: {enemy-kill: +10, time-bonus: true}

levels:
  source: files-txt                 # Рівні/Формат
  count: 3
  progression: unlock-sequential

ui:
  frontends: [console, gui-pygame]  # спільний двіжок — вимога архітектури
  screens: [menu, game, results]
```

## Звʼязка з таксономією ([T33](../../tasks/.t/T33-B--task-taxonomy.md))

- Кожен таск каталогу (крім зон «Код» і «Супровід») знає, **який фрагмент спеки він додає**: таск «+HP у гравця» → `entities.player.params.hp`; «карта-тор» → `field.topology: torus`; «перемога: всі вороги знищені» → `rules.win`.
- Тоді сума набраних тасків = спека, і навпаки: спека читається як список тасків із цінами. Каталог і спека — **одна модель даних із двох боків** — це усуває ручну синхронізацію «що заявлено ↔ що оцінюється».
- Таски зон «Код і платформа» та «Супровід» — не про гру, вони у спеку не входять (живуть лише в заявці).

## Що це дає одразу (навіть у MVP)

- Чек-ліст захисту генерується без ручної роботи: по фрагменту спеки — критерій перевірки з картки таска.
- Формальна різниця варіантів між студентами (перетин спек у відсотках).
- Пізніше, не в MVP: рушій-скелет, що вміє інтерпретувати частину спеки (рух, взаємодії) — але це вже інша історія, спека цінна й без нього.

## Ризики і межі

- Не все декларативне: унікальні студентські механіки не ляжуть у фрагменти — для них передбачити `custom`-фрагмент із вільним описом (і ручною ціною) — spec лишається повним, просто менш формальним у цьому місці.
- Не перетискати: спека — модель заявки й захисту, а не вимога до архітектури студентського коду (його гра не мусить читати YAML).
